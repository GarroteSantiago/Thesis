# C6: Naming in message-based systems

## Definition
How a sender names a receiver or an object on another node or core: hardware translation tables, global object identifiers with a home node, name servers, or capabilities used as the only names. Merges "name translation (XLATE/ENTER)", "exposed translation cache", "global name translation", "global name space / object identifiers", "home node and object migration", "fanout bottleneck", "Global Translation Lookaside Buffer / Global Destination Table" and "centralised namespace".

## First found in
P12

## What the papers say, compared
- **Hardware translation on each node.** The MDP translates global object identifiers in an associative on-chip memory that also serves as a method cache (P69, pp. 189, 193); later versions expose it as ENTER/XLATE instructions "a systems programmer can use for any translation" (P64, pp. 12–13; P12, p. 7). The M-Machine caches a software Global Destination Table in a GTLB per node (P66, p. 7).
- **The MDP's own evaluators judge its naming insufficient.** The translation tables are "inadequate to transparently and inexpensively provide a global name space" (P65, p. 11). In the kernel above, each object has a home node that tracks it, and that node becomes a "fanout bottleneck" for popular immutable objects (P70, pp. 63–64, 68, 119).
- **Operating systems use name services, central or replicated.** Barrelfish maps service names to references through a name service, without saying whether it is one instance (P8, p. 10). fos holds the directory in a fleet of name servers cached by each microkernel (P102, pp. 5–7). Helios keeps the namespace in one coordinator kernel, "the only component of Helios that relies on centralized control", at the cost of two remote channels to set up a connection on the same kernel (P45, pp. 6, 8). Minix 3 uses one data-store name server and Singularity one root name server (P49, pp. 47–50).
- **Capabilities avoid a name service.** In KeyKOS naming is "intrinsically decentralized" because capabilities are the only names (P53, pp. 3–6). L4 moved from global thread identifiers, which leaked covert channels and pushed servers onto a "gateway thread, which could become a bottleneck", to capability-named endpoints (P48, pp. 137–138, 143).
- **Comparison.** Every non-capability scheme read has a central point or a bottleneck the authors name (P45, P49, P65, P70); only Helios gives a cost, and none measures a decentralised alternative.
