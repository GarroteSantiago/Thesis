# C39: Garbage collection and memory reclamation support

## Definition
How objects are reclaimed, and whether hardware helps. Merges "Generation Scavenging", "ephemeral garbage collection", "generation tags (hardware write barrier)" and "storage resource object (global heap vs local stack)".

## First found in
P11

## What the papers say, compared
- **Software collectors won.** Generation Scavenging uses about 3% of CPU time with "no hardware support" (P11, pp. 50, 86, 110, 126), and SOAR's GC hardware "probably did not speed up SOAR" (P11, p. 72); its generation tags could be done by the compiler for about 1–2% (P261, p. 7). Moon's ephemeral collector for Lisp machines was "subsequently adapted for use on stock hardware", and the belief that stock Lisps could never match GC performance was "proven wrong" (P15, pp. 13, 27, 34–35).
- **The 432 avoided it for short-lived objects.** Global heaps need garbage collection, so local stack storage objects were added because collection "is prohibitive for short-lived objects" (P72, pp. 179–181).
- **In a message machine, global collection is hard.** The J-Machine kernel had none; a parallel algorithm tracking every sent ID "would be unfeasible", and mark-and-sweep "has to stop the J-Machine" (P70, pp. 58, 120).
- **Comparison.** On one processor, hardware GC support did not pay; on a machine of message-passing nodes, no collector was found that avoids a global stop.
