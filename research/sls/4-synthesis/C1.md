# C1: Message-driven processing

## Definition
A processor whose control is driven by arriving messages: the hardware buffers each message and starts a task to handle it, so there is no receive instruction. Merges the records' "message-driven processor", "no receive instruction", "message dispatch as task creation", "message queue as activation stack", "direct execution of messages" and "message unit / instruction unit split".

## First found in
P12

## What the papers say, compared
- **The designers, across one machine line and six years, agree on the idea.** The 1987 design has a controller "driven by the incoming message stream", with "no instructions ... required to receive or buffer the message" and a separate message unit and instruction unit (P69, pp. 189, 191–192). The 1989 paper puts it as "There is no receive instruction. A task is created for each arriving message" and compares the message queue to a stack of method activations (P64, pp. 4, 8–9). The 1992 node creates a task in 3 cycles (P12, pp. 1, 9); the 1993 evaluation measures dispatch in four cycles, with two priority queues and a background level (P65, p. 2). The kernel and language on top are "almost completely message-driven" (P70, pp. 2, 176).
- **How far the claim reaches differs.** Within a node the MDP still has ordinary local loads, stores and traps (P69, pp. 189, 194; P12, p. 8), so message semantics hold fully only between nodes.
- **A third party disagrees on whether hardware support pays.** The Active Messages authors say message-driven hardware lacks locality: a context lasts one handler, so large register sets cannot be used, making the support "partly counter-productive" (P33, pp. 435–437). They add that the J-Machine "does not actually support the message driven programming model fully" (P33, p. 437). The designers instead credit message-driven control for their low overhead (P69, pp. 195–196; P12, pp. 10–11).
- **The measured overhead sits above the hardware.** On the J-Machine, about 70% of active time goes to the operating system (P70, p. 104), so a fast hardware dispatch does not make the whole send cheap (see C12).
- **Other machines that receive messages are not message-driven.** The M-Machine handles arrivals in a dedicated event thread, with no new task per message (P66, pp. 4–7). On the Lisp Machine a send is a function call (P73, p. 285). Machines that treat the network "essentially as a fast I/O device" are the contrast case the Active Messages paper names (P33, p. 431).
