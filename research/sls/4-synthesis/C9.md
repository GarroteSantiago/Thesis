# C9: Synchronous (rendezvous) IPC

## Definition
Sender and receiver meet: the message is copied directly when both are ready, and the caller blocks until the reply. Merges "synchronous (rendezvous-style) IPC", "rendezvous message passing", "direct process switch", "resume key", "entry capability / resume capability" and "protected control transfer (Exokernel)".

## First found in
P46

## What the papers say, compared
- **Several kernel lines chose it.** In the original L4 it was "the only communication, synchronisation, and signalling mechanism" (P48, pp. 136–137); on IPC the kernel switches straight to the partner on the caller's time slice (P48, p. 145). Minix 3 passes "fixed-length messages using the rendezvous principle" (P49, p. 48). KeyKOS invokes keys by call, fork and return, with the kernel building a resume key for the reply (P53, pp. 3, 7); EROS consumes every copy of a resume capability on use, "ensuring an 'at most once' reply" (P77, p. 173). Exokernel's protected control transfer "crosses address spaces but does not transfer arguments" (P46, p. 74).
- **The 432's procedure call behaves the same way** by call and return semantics, though the paper does not use the word (P10, p. 321).
- **L4 found limits after 20 years.** Synchronous-only IPC "forces a multi-threaded design onto otherwise simple systems" and RPC-style IPC "sequentialises client and server" across cores, so asynchronous notifications were added (P48, pp. 136–139; see C10, C15).
- **Comparison.** The single-core kernels read (L4, Minix 3, KeyKOS, EROS) agree on synchronous IPC; the only paper with experience on multicore (P48) reports it as a limit there.
