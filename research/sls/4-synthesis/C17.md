# C17: Replicated state kept by agreement

## Definition
State that a shared-memory operating system would share is kept as a replica on each core, made consistent by message protocols between them. Merges "replicated (not shared) state", the multikernel "monitor" role, "microkernel to OS layer delegation" (cached answers) and "best-effort OS interfaces".

## First found in
P8

## What the papers say, compared
- **Barrelfish is the measured case.** Potentially shared state is a local replica kept consistent by agreement among per-core monitors (P8, pp. 6–7, 9). Unmap uses a one-phase commit and retype a two-phase commit among all monitors (P8, p. 11); the two-phase commit takes about 14k to 28k cycles over 2 to 32 cores and "serializes more messages" than a TLB shootdown (P8, p. 14). All cores must keep their capability lists consistent (P8, p. 10).
- **Its own authors list the costs.** Replica consistency adds latency and burden on developers (P8, p. 7), and in hindsight the decentralised capability scheme "was a mistake ... unnecessarily complex, and no more efficient than scalable per-processor memory managers" (P8, p. 10).
- **fos caches instead of agreeing.** Microkernels cache name and privilege answers from server fleets and invalidate them by message (P102, pp. 5–7); some interfaces return information "which may be slightly out of date" for speed (P102, p. 2).
- **Others avoid replication.** Helios keeps naming central rather than replicated (P45, p. 6; see C18). On the J-Machine, kernel data structures are replicated on every node (P70, pp. 2, 56), but objects keep one home node (C6).
- **Comparison.** Only Barrelfish measures agreement, and its authors judge one of their replicated designs not worth its cost; no paper read compares a replicated and a central version of the same function.
