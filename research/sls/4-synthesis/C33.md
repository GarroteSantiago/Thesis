# C33: Functional migration

## Definition
Moving a function (an operating system service, a language operation, a check) between software, microcode and hardware. Merges "functional migration" and "migrating functionality between levels of abstraction".

## First found in
P10

## What the papers say, compared
- **Upward, in the 432.** OS functions, language operations, object addressing and fault handling were migrated into microcode and hardware (P10, pp. 296, 298–299); type managers are "partially in hardware ... and partially in operating system software" (P72, pp. 173, 184–185). Colwell et al. find that even if IPC and procedure calls "were free, executing in zero time", the 432 would still be slow (P10, pp. 301, 309).
- **Both ways, in SOAR.** "the key to good performance is a willingness to migrate functionality from one level of abstraction to another"; SOAR replaced microcoded instructions with software trap handlers (P11, p. 126).
- **Minimal hard-wiring in the MDP.** Only one message is hard-wired and the rest are ROM code (P69, p. 191).
- **Comparison.** The papers agree migration should follow measurement, not the level's prestige; the 432 is the cautionary case and SOAR the counter-example (C35, C36).
