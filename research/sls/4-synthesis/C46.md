# C46: Mixing messages with shared state

## Definition
Systems and programs that use shared memory, locks or direct calls alongside messages, and the reasons given. Merges "mixing message passing with other synchronization", "communication through shared Lisp objects" and the shared-state parts of "notional lock / lock server" and "single-owner shared heap".

## First found in
P9

## What the papers say, compared
- **Measured frequency (programs).** In six Go applications, shared-memory primitives are used more than channels (Mutex 45.01–70.34% against chan 18.48–42.99% of uses), stable from 2015 to 2018, and 16 blocking bugs mix a channel with a lock or wait; no developer reason is recorded (P9, pp. 4, 6–7, 11).
- **Reasons from system designers.**
  - Existing programs: Barrelfish supports threads sharing an address space because "most current programs" need it (P8, pp. 11, 15).
  - Performance: Singularity keeps a shared object heap, since if all data "had to go over channels, the system would be very slow" (P49, p. 50); L4 prefers shared buffers for bulk data (P48, pp. 136–138).
  - Ease of programming: "shared memory access simplifies programming" (P66, p. 6); application shared memory "can be quite useful" in small applications (P102, p. 2).
  - Debugging and interaction: Lisp Machine processes communicate "in arbitrary ways through shared Lisp objects", and the contract is unenforced so state can be examined from a debugger (P73, pp. 282, 429).
  - Compatibility: KeyNIX shares UNIX tables in a segment (P53, pp. 11, 17).
  - Atomicity: Concurrent Smalltalk provides locks for atomic transactions (P70, pp. 11, 54); fos needs a lock server (P102, p. 8).
  - Speed of calls: sends to known types become direct calls (P12, p. 20).
- **Comparison.** Every system read mixes; reasons range over performance, compatibility, convenience and atomicity. Only P9 measures, and none of the papers read asks developers why (P19 unread).
