Proceedings of the 13th International Conference on Architectural Support for Programming Languages and Operating Systems (ASPLOS '08), Seattle, pp. 329–339 (page range from Crossref; the PDF prints no page numbers). https://doi.org/10.1145/1346281.1346323

## First pass: the five Cs
- **Category:** Empirical defect study: a manual characteristic study of 105 real concurrency bugs taken from the bug databases of four open-source applications (P5, p. 329, p. 330).
- **Context:** Builds on general bug-characteristic studies (IBM defect types [38], operating system errors [8]) and on the single prior concurrency bug-pattern study [11], which used bugs written on purpose by students (P5, p. 330, p. 338); targets data race, atomicity-violation and deadlock detectors, interleaving testing and transactional memory (P5, p. 329–330).
- **Correctness:** The assumptions are stated: the four C/C++ applications represent server and client programs; fixed, reported bugs matter more than unreported ones; the authors know the code from earlier work (P5, p. 332). The paper says it does not claim generality beyond these applications and languages (P5, p. 330, p. 332).
- **Contributions:** 13 findings on bug pattern (atomicity and order violation), manifestation (threads, variables, accesses), fix strategy and avoidance by transactional memory, each with an implication for detection, testing or language design (P5, Table 1, p. 331).
- **Clarity:** Well structured: definitions in Table 2, per-application tables for every finding, worked code examples (Figures 1–9) (P5, p. 332–337). Some table layouts are dense but every number in the abstract can be traced to a table.

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| new: atomicity violation | "The desired serializability among multiple memory accesses is violated": a region meant to be atomic is not enforced; 51 of 74 non-deadlock bugs | p. 332, p. 333 |
| new: order violation | "The desired order between two (groups of) memory accesses is flipped"; 24 of 74 non-deadlock bugs; "many" are missed by existing race and atomicity detectors; some can be fixed with coarser-grained locking, others cannot be fixed by locks | p. 332, p. 334, p. 336 |
| new: manifestation condition | "A specific execution order among a smallest set (S) of memory accesses" that guarantees the bug manifests, measured in threads, variables and accesses | p. 332 |
| new: multi-variable concurrency bug | Unsynchronized accesses to correlated variables leave inconsistent state; 25 of 74 non-deadlock bugs; missed by single-variable detectors | p. 335 |
| new: data race (not a bug pattern) | Two conflicting accesses to one shared variable without proper synchronization; excluded as a category because races can be benign and "data-race free does not mean concurrency bug free" | p. 329, p. 332 |
| new: deadlock | "Two or more operations circularly wait for each other to release the acquired resource"; 7 of 31 involve one thread acquiring a resource it already holds | p. 329, p. 334 |
| new: order intention | A programmer's expectation that A precedes B (or that A runs before B or not at all); "cannot be easily enforced by the basic TM design or locks"; the "before B or not at all" sub-type occurs in 7 bugs; 20 of 105 bugs cannot benefit from basic TM, their violated intentions being "such as order intentions" | p. 338 |

## Notes
- **Source:** full text, author-hosted PDF https://pages.cs.wisc.edu/~shanlu/paper/asplos122-lu.pdf (identical file also at cs.columbia.edu), 11 pages, ASPLOS '08 camera-ready with the ACM copyright block; saved as `research/papers/P5.pdf`. Page numbers cited are the proceedings pages 329–339 (from Crossref); PDF page k is proceedings page 328 + k.
- **Text extraction:** pdftotext merges the abstract with the first introduction column (the "Abstract" heading prints empty); the abstract content was read from that merged text (P5, p. 329).
- **I3 fit:** the paper reports counts for programs that communicate through shared variables and locks (P5, p. 332–336) but never calls them "shared-memory" programs, and gives no split by communication mechanism. Its own example of a message-queue bug in Mozilla (P5, p. 336) shows that at least one studied program also uses messages internally. So the "shared memory only" label in R0-005 is an inference by the reader, not something the paper states.
- **SQ7 relevance:** the only message-related defect is Mozilla #131447, which the paper counts in the "Design" fix category (P5, p. 336). Using this paper as a shared-memory baseline needs that caveat.
- **Generality:** the authors limit their findings to C/C++ server and client applications. Scientific programs, operating systems and Java are explicitly not covered (P5, p. 332).
