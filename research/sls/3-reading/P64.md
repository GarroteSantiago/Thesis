## First pass: the five Cs
- **Category:** Design description of a planned machine (the J-Machine and its node, the Message-Driven Processor, MDP), written at the "advanced design stage", with design figures and no evaluation section (pp. 1, 13).
- **Context:** Message-passing multicomputers (Caltech Cosmic Cube, Intel iPSC, N-CUBE, Ametek), shared-address machines (BBN Butterfly, IBM RP3), single-chip nodes (InMOS transputer, Caltech MOSAIC) (p. 3); concurrent models it aims to support: actors, dataflow, communicating processes (pp. 1–2); the authors' own earlier MDP and network papers [5–10, 12–15] (pp. 3, 6, 14).
- **Correctness:** The premise is that "A fast network is of little use if very large overheads are required to initiate and receive messages at the processing nodes" (p. 7) and that the difficulty "is not developing the mechanisms conceptually. It is implementing them efficiently" (p. 5). Both are argued, not measured; the only comparison is delivery plus dispatch "< 3µs on the J-Machine as opposed to 5ms on an iPSC" (p. 3).
- **Contributions:** A message-driven node: a SEND instruction, automatic hardware buffering into two priority queues, and a dispatch mechanism that creates a task per arriving message in one clock cycle, with "no receive instruction" (pp. 7–9); tags for futures and c-futures (p. 12); ENTER/XLATE translation instructions exposing a set-associative cache to support a global virtual address space (pp. 12–13); a 3-D mesh network of up to 65,536 nodes (pp. 2, 5).
- **Clarity:** Short and clear, with a worked end-to-end example (Sum message, Figure 1, pp. 4–5) and assembly fragments (Figures 4, 6; pp. 8, 10). The scan is legible; the OCR text layer has errors in units (µs), checked against the page images.

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| new: message-driven processor | "A conventional processor is instruction-driven ... A message-driven processor receives a message from the network and dispatches a control sequence to execute the task specified by the message." | p. 4 |
| new: no receive instruction (task per message) | "There is no receive instruction. A task is created for each arriving message to handle that message. A computation is advanced (driven) by the messages carrying tasks about the network." | p. 8 |
| new: message queue as activation stack | "Each message stored in the MDP message queue represents a method activation much as each stack frame allocated on a push-down stack represents a procedure activation." | p. 9 |
| new: fine-grain concurrent computer (grain size) | Fine-grain programs have many short (≈ 20 instruction) tasks; fine-grain nodes fit on one chip with ≈ 10^4 bytes of memory. | p. 2 |
| new: general mechanisms rather than a hardwired model | "It provides general mechanisms for communication, synchronization, and translation rather than hardwiring mechanisms for a specific model of computation." | p. 13 |
| new: unifying shared memory and message passing | "The MDP provides a virtual addressing mechanism intended to support a global name space while using an execution mechanism based on message passing." | p. 12 |
| new: c-future / future tags | Tags that fault on access to data not yet arrived; c-futures suspend a task awaiting a reply and are cheaper than copyable futures. | p. 12 |
| new: exposed translation cache (ENTER/XLATE) | A set-associative cache "exposed ... in a pair of instructions that a systems programmer can use for any translation". | pp. 12–13 |
| new: jellybean node | "Each message driven processing node is a jellybean part", fabricable in DRAM-like commodity technology. | p. 13 |

## Notes
- **Source read:** full text, `research/papers/P64.pdf`, downloaded in this run from the Internet Archive DTIC mirror (https://archive.org/download/DTIC_ADA211909/DTIC_ADA211909.pdf); the DOI resolves to DTIC, whose PDF URLs returned HTTP 403. Version: MIT VLSI Memo No. 89-532 (May 1989), a scanned preprint of the IFIP Congress 89 paper, 17 PDF pages, printed pages 1–15. Numbers in µs were checked against the page images because the OCR text layer garbles them.
- **Dates:** the memo is dated May 1989 (PDF p. 1), but the conclusion says "At the time of this writing (January 1988)" (p. 13). Status claims hold for January 1988.
- **Design figures:** every number in the paper is a design or analytical figure; network delays are what "The network is expected to have" (p. 6). None comes from silicon.
- **Criterion:** I1 is confirmed from the full text: (a) SEND instruction and (b) hardware buffering and dispatch (pp. 4, 7–9). No exclusion criterion found: it is a university technical report of 15 pages (X5), the message mechanism is in each node's instruction set and hardware, not only in the interconnect (X3), and the machine is "a general purpose parallel computer" (p. 13, X4).
- **SQ9 (field n/a under I1):** the authors argue for "general mechanisms ... rather than hardwiring mechanisms for a specific model of computation" (p. 13), and that the mechanisms "have been selected to be both general and amenable to efficient hardware implementation", supporting actors, dataflow and communicating processes (pp. 1–2).
- **SQ10 (field n/a under I1):** the MDP is "an experiment in unifying shared-memory and message-passing parallel computers": a global name space on a message-passing execution mechanism (p. 12). No properties or performance kept or lost are reported.
- **SQ2 note:** the network relies on hardware for reliability: "There is no acknowledgement, error detection, or error correction on the network channels", justified by short wires in one cabinet (p. 6).
