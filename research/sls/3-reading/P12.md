## First pass: the five Cs
- **Category:** Design and implementation description of a working processor chip (the MDP) and its multicomputer (the J-Machine), with cycle counts but no evaluation section (pp. 1–3, 13–18).
- **Context:** Message-passing multicomputers (Cosmic Cube, iPSC, N-CUBE, Ametek), shared-address machines (BBN Butterfly, IBM RP3), single-chip nodes (Transputer, MOSAIC, iWARP); the authors' earlier MDP architecture paper [11] (p. 6) and k-ary n-cube network work [10, 12, 14] (pp. 2–3; [13] p. 12).
- **Correctness:** The premise is that sequential-processor mechanisms do not support synchronisation, communication and global naming efficiently, so these "must be implemented largely in software with prohibitive overhead" (p. 2). It is argued, and backed only by one comparison with iPSC message times (p. 2). The cycle counts are given as design facts, not as measurements (pp. 9–11).
- **Contributions:** A single-chip node in which message arrival creates and dispatches a task in hardware, with no receive instruction (p. 1). It adds SEND instructions, hardware message queues, presence tags (FUT/CFUT), name translation (XLATE/ENTER) and three priority register sets (pp. 5–9). The chip is running silicon (p. 16), and Concurrent Smalltalk and Id are implemented on it (pp. 20–23).
- **Clarity:** Clear and well structured, with worked assembly examples (combining tree, CALL handler, size-of-tree; pp. 5, 10–11, 22). In this preprint most figures are blank and only their captions remain (see Notes).

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| message-driven processing (new) | "processing is performed in response to messages (via the dispatch mechanism). There is no receive instruction. A task is created to handle each arriving message." | p. 1 |
| primitive mechanisms vs programming models (new) | Mechanisms are the hardware's primitive operations from which programming abstractions are built. The MDP gives general communication, synchronisation and naming mechanisms instead of specialising for one model. | pp. 1–2 |
| message dispatch as task creation (new) | The header opcode is loaded into the IP and a message segment descriptor goes into A3, creating a task in 3 cycles. | p. 9 |
| presence tags / futures (FUT, CFUT) (new) | Tagged locations are marked empty, and reading one faults and suspends the task until a value is written. Used for synchronisation. | pp. 6–7 |
| name translation (XLATE/ENTER) (new) | A hardware associative table maps arbitrary keys to values (segment descriptors or node numbers) to support a global virtual address space. | p. 7 |
| fine-grain multicomputer / jellybean node (new) | An inexpensive node with small memory, many per system, giving more performance per unit cost. Tasks are about 20 instructions and objects about 8 words. | pp. 1–2, 23 |
| global virtual address space over message passing (new) | The same IDs name local and remote objects. A shared-memory model can be built on the mechanisms. | pp. 3, 5 |
| selector-object dispatch (new) | CST method invocation is a message to the first argument. COSMOS picks the function by class from a selector object; known types bypass it with a direct call. | pp. 20–21 |
