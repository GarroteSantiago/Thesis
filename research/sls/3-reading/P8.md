# P8

## Reference
Andrew Baumann, Paul Barham, Pierre-Evariste Dagand, Tim Harris, Rebecca Isaacs, Simon Peter, Timothy Roscoe, Adrian Schüpbach, Akhilesh Singhania (2009). *The Multikernel: A New OS Architecture for Scalable Multicore Systems*. Proceedings of the ACM SIGOPS 22nd Symposium on Operating Systems Principles (SOSP '09), pp. 29–44 (Crossref). https://doi.org/10.1145/1629575.1629579. P8, from row R0-008. Included under I1(c): a kernel in which "all inter-core communication is performed using explicit messages" (p. 5).

Page numbers below are the PDF pages of the 20-page copy on sigops.org. Each page also carries that number at the foot. They are not the ACM proceedings pages 29–44.

## First pass: the five Cs
- **Category:** A new OS architecture (the multikernel), a prototype that implements it (Barrelfish), and a measured evaluation on x86-64 multiprocessors (pp. 1–2, 8).
- **Context:** Distributed systems applied to OS structure. The paper builds on Lauer and Needham's duality of message and shared-memory OSes (p. 3), URPC/LRPC (pp. 3, 8–9), exokernel (p. 8), seL4 capabilities (p. 10), Tornado/K42 clustered objects and Corey (p. 17), microkernels (L4) and Disco (p. 17), and fos (p. 17).
- **Correctness:** Its assumptions are that hardware is becoming a network (pp. 3, 6), that cores are becoming diverse (p. 3), that cache coherence will grow costly or disappear (pp. 4–5) and that messages cost less than shared memory as more cache lines are touched (pp. 3–4). The first three are argued from trends and citations. Only the last is measured (Fig. 3, on 16 cores of one machine).
- **Contributions:** (1) the multikernel model and its three principles: explicit communication, hardware-neutral structure and replicated state; (2) Barrelfish, a concrete multikernel; (3) measurements showing scalability, adaptability to hardware and competitive performance (p. 2).
- **Clarity:** Well written and clearly structured. Design choices that follow from the model are kept apart from engineering choices (pp. 7, 11). Some figure values can only be read off plots.

| Receiving unit and state ownership | The receiver is a dispatcher. A process is a set of dispatcher objects, one per core, and "communication … is not actually between processes but between dispatchers (and hence cores)" (p. 9). | Message mechanism | Inter-core transport: URPC, a shared-memory region used as a point-to-point channel for cache-line-sized messages between one writer and one reader. The receiver polls the last word of the line (p. 9). Prefetching for pipelined throughput can be chosen at channel setup (p. 9). The model is asynchronous and split-phase (pp. 6–7). Same-core IPC is an asynchronous, fixed-size message from the CPU driver, with an optional synchronous LRPC/L4-like call (p. 8). Naming: a name service maps service names to a service reference, used to set up a channel through the monitors (p. 10). All transports sit behind a common interface, with marshalling generated by a stub compiler (p. 10). Ordering and delivery: "a multikernel may exploit reliable in-order message delivery" (p. 17); no further guarantee is stated. Buffering: the throughput test uses a queue of 16 messages (p. 10); full-queue behaviour is not stated. Busy or absent receiver: the dispatcher polls for a fixed time, then blocks and asks its monitor for notification, and an IPI wakes it (pp. 9, 14). Remote monitors handle messages when "convenient" (p. 12). Dispatch: user-level message dispatching and event demultiplexing code in the threads package (pp. 9, 13). | pp. 6–10, 12–14, 17 |
| Non-message primitives | (1) Cache-coherent shared memory as the hardware carrier of every inter-core message. Reason: it is the only mechanism on current hardware (p. 9). (2) Shared memory for the message channels themselves (p. 5). Same-core, "more complex communication channels are built over this using shared memory" (p. 8). (3) Application shared memory and shared address spaces across cores, optionally one shared hardware page table. Reason: most current programs need it, and the shared table is "typically more efficient" (pp. 5, 11). (4) Traps and system calls into the privileged CPU driver; capability operations are system calls (pp. 8, 10). (5) Device interrupts are routed in hardware, then demultiplexed by the CPU driver and turned into messages (p. 8). (6) IPIs and MONITOR/MWAIT to wake or idle a core, used instead of spinning forever (pp. 9, 14). (7) Cache prefetch instructions in URPC (p. 9). (8) DMA by the NIC (p. 15). (9) Future work: a replica shared by closely coupled cores under spinlocks, to use shared caches (pp. 7, 18). | pp. 5, 7–11, 14–15, 18 |
| Self-definition | Not object-based. The OS is split into a privileged CPU driver, written in C and assembly and specialised for x86-64 (7135 + 337 lines), and user-level monitors and services that talk by messages (p. 8). The CPU driver lies outside the message model and is the base: it serially processes traps and interrupts (p. 8). Whether a running program can inspect or change these levels: not stated. The closest mechanism is the system knowledge base, which holds hardware facts in first-order logic for queries such as transport selection (p. 11). Cost of the split: OS invocations become local RPCs with two context switches, "several thousand cycles" (pp. 11–12). | pp. 8, 11–12 |

Coordination is involved: yes, because all cores must keep their capability lists consistent (p. 10). *Scheduling*: the CPU driver time-slices locally and runs dispatchers by upcalls, with user-level thread schedulers (pp. 8–9). ## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| new: multikernel | An OS structured "as a distributed system of cores that communicate using messages and share no memory". | p. 5 |
| new: explicit inter-core communication | All inter-core communication uses explicit messages; no memory is shared except message channels. | p. 5 |
| new: hardware-neutral OS structure | Only the message transports and the hardware interface are machine-specific. | p. 6 |
| new: replicated (not shared) state | Potentially shared state is accessed as a local replica, with consistency kept by messages and agreement protocols. | pp. 6–7 |
| new: split-phase operation | An operation sends a request and continues, and the reply arrives later. | p. 6 |
| new: late binding of protocol and transport | The protocol and transport are chosen at runtime to fit the hardware or workload. | p. 6 |
| new: pipelining and batching of messages | Several requests in flight, or several requests in one message, give more throughput per core. | pp. 2, 6 |
| new: CPU driver | Per-core, privileged, event-driven, single-threaded, nonpreemptable kernel part that shares no state with other cores. | p. 8 |
| new: monitor | Per-core user-level process that coordinates system-wide state through agreement protocols. | p. 9 |
| new: dispatcher | Per-core representative of a process; the unit that communicates. | p. 9 |
| new: URPC | User-level RPC: a shared-memory, cache-line, point-to-point channel received by polling. | p. 9 |
| new: system knowledge base (SKB) | Hardware facts in first-order logic, queried for policy (e.g. building multicast trees). | p. 11 |
| new: spectrum of sharing and locking | Traditional OSes moved from the far left towards finer-grained locking and more replication. The multikernel sits at the extreme right, where all state is replicated and kept consistent by agreement protocols. | p. 5 |
| new: multikernel vs microkernel | A microkernel uses messages between processes but "remains a shared-memory, multithreaded system in the kernel". | p. 17 |
| new: message-passing/shared-memory duality | Lauer and Needham: the two OS models are duals, and machine architecture decides between them. | p. 3 |

## Notes
- Source: full text, PDF from https://www.sigops.org/s/conferences/sosp/2009/papers/baumann-sosp09.pdf (20 pages, pdfTeX, created 2009-08-10), saved as `research/papers/P8.pdf`. It is the camera-ready layout, not the ACM DL version: Crossref gives pp. 29–44 for the ACM version, and all page numbers here are the 20-page copy's. All 20 pages were read (third pass), and the figure values marked "read off" were estimated from rendered plots of Figs. 6–9.
- No C IDs could be reused, because no `sls/4-synthesis/C*.md` was among the inputs. All concepts are marked new.
- SQ-relevant point not captured above: the authors argue for a future where hardware drops cache coherence and an OS based on native message passing fits best (p. 5). Yet their own messages are built on coherence, and they tuned URPC to the coherence protocol (pp. 9, 17). The case for messages as a hardware primitive is therefore argued, not tested, in this paper.
- In hindsight the authors call the decentralised capability design "a mistake" (p. 10), which is evidence for SQ4/SQ15 on the cost of decentralised resource allocation.
