## Reference

Proceedings of the 24th International Conference on Architectural Support for Programming Languages and Operating Systems (ASPLOS '19), ACM, pp. 865–878. https://doi.org/10.1145/3297858.3304069. P ID: P9 (row R0-009). Included under I3.

## First pass: the five Cs
- **Category:** Empirical study of real-world concurrency bugs: "the first systematic study on concurrency bugs in real Go programs", 171 bugs from six applications (P9, p. 1).
- **Context:** Builds on earlier real-world bug studies, mainly of C, C++ and Java (Lu et al. ASPLOS '08 [45], TaxDC [40], Node.js [57]), and on deadlock and race detection work (P9, pp. 1, 5, 12). It sets out to test Go's claim that "explicit message passing is less error-prone" than shared memory (P9, p. 2). It cites earlier static checkers for Go channels (Lange et al. [38, 39], Ng and Yoshida [49]) (P9, p. 12).
- **Correctness:** The assumptions are mostly sound, but the sampling is under-reported. Bugs were found by searching commit logs for keywords (3211 matching commits), then randomly sampling those commits and studying them by hand (P9, p. 5). The paper does not say how many commits were sampled. It does not say who classified each bug, and it gives no agreement figure between classifiers. Only bugs that were fixed and well documented were kept (P9, p. 6). One claim, that message passing is "even more likely" to cause blocking bugs, divides bug counts by static counts of primitive use (Table 4). It does not measure how often each primitive is exercised at run time (P9, pp. 4, 6).
- **Contributions:** (1) The first empirical study of Go concurrency bugs, in six production applications. (2) Nine observations and eight implications about bug causes, fixes and detection. (3) A taxonomy along two orthogonal dimensions: behaviour (blocking or non-blocking) and cause (shared memory or message passing). Study data is published at github.com/system-pclub/go-concurrency-bugs (P9, p. 2).
- **Clarity:** Clear and well organised. Each section ends with numbered Observations and Implications, and counts are in Tables 5–12 (P9, pp. 5–11). The numbers in the tables match the numbers in the text.

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| New: blocking bug | One or more goroutines are unintentionally stuck and cannot move forward. This is broader than deadlock, because it includes waiting with no circular wait for a resource that no other goroutine supplies. | p. 5 |
| New: non-blocking bug | All goroutines finish their tasks, but their behaviour is not the one intended. | p. 5 |
| New: cause dimension (shared memory vs. message passing) | Bugs are classified by how goroutines communicate: by misprotecting shared memory or by misusing message passing. | pp. 2, 5 |
| New: message passing is less error-prone (common belief, refuted for blocking bugs) | "Contrary to the common belief", message passing causes 58% of blocking bugs, while shared-memory primitives are used more. Message passing causes fewer non-blocking bugs. | pp. 2, 6, 10–12 |
| New: mixing message passing with other synchronization | Using channels together with locks, wait, or libraries (`context`, `time`, `Pipe`) gives blocking bugs that are "very hard to detect". | pp. 2, 7, 12 |
| New: channel usage rules | The rules Go enforces on its channels: no use before initialization, no double close, no send on a closed channel, and every send or receive needs a matching partner. Breaking these rules is "one major reason" for concurrency bugs. | pp. 2, 3, 12 |
| New: data race through a message-passed reference | Sending a reference to a shared variable over a channel can cause a data race. | p. 9 |
| New: Go's new implementation of existing primitives | The same primitives as in other languages can cause new bugs because Go implements them differently, for example RWMutex giving writers priority. | p. 6 |

## Notes
- **Source:** the authors' PDF at https://songlh.github.io/paper/go-study.pdf (14 pages; acmart LaTeX, created 2019-03-22). It has the same title, DOI and ASPLOS '19 copyright block as the ACM version. The ACM Digital Library PDF link returned an HTML page and was not used. The authors' PDF is saved as `research/papers/P9.pdf`.
- **Page convention:** page numbers in this record are the PDF's pages 1–14. The proceedings page is 864 plus the PDF page (865–878, per Crossref).
- **Checks:** the counts in Tables 5, 6 and 9 add up to the totals in the text (36 + 69 = 105 shared memory; 49 + 17 = 66 message passing). The 42% and 58% split is 36 and 49 of 85 blocking bugs (pp. 5–6, 9).
- **Q9 for I3:** `quality.md` defines Q9 for evaluating a system. Here the system evaluated is incidental: Go's built-in detectors (pp. 8, 11). Answered yes because no author built them, but an I3 study arguably "does not evaluate a system", which would make it "no".
- **SQ7 relevance:** this is a within-language comparison. Both mechanisms are in the same programs, and channels sit on top of a language that also has shared memory. It is not a system built on message passing only (pp. 2–3).
- **Extra artefact:** the authors built a detector for anonymous-function races that found new bugs, one confirmed by developers (p. 12). It is not evaluated in the paper.
