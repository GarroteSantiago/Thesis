## First pass: the five Cs
- **Category:** A design-and-implementation paper with measurements. It proposes a communication mechanism (Active Messages), implements it on two commercial message-passing multicomputers, compares it with message-driven machines and outlines hardware support for it (p. 430, p. 431 §1.3).
- **Context:** Message-passing multicomputers (nCUBE/2, iPSC, CM-5) that treat the network "essentially as a fast I/O device", set against message-driven architectures (J-Machine, Monsoon) that "integrate the network deeply into the processor" (p. 431). It builds on the authors' own TAM work [3] (p. 437, p. 440) and on Monsoon [17] (p. 431, p. 436, p. 440).
- **Correctness:** The premises are stated: communication must have a low start-up cost and must overlap with computation (cost model, p. 430). The claim that message-driven processors lose processing performance through lack of locality is argued, not measured (p. 435, p. 436–437).
- **Contributions:** (1) Active Messages: each message carries the address of a user-level handler that runs on arrival (p. 431). (2) Implementations on nCUBE/2 and CM-5 with measured costs (p. 433–434). (3) Split-C, split-phase PUT/GET on Active Messages (p. 434). (4) The argument that the message-driven model can be simulated on Active Messages, with TAM as the compilation target (p. 437–438). (5) A design space of network-interface and processor support for Active Messages (p. 438–439).
- **Clarity:** Clearly written, with tables and figures. The scanned facsimile has OCR defects in the text layer, and Table 1's columns had to be read from the page image (p. 432).

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| Active Messages (new) | Each message carries at its head the address of a user-level handler, which runs on arrival with the body as argument, runs quickly to completion, and only integrates the data into the ongoing computation. | p. 431 |
| Message-driven architecture (new) | Message reception is part of instruction scheduling and send is in the execution unit (J-Machine, Monsoon). The handler performs the computation and may suspend. | p. 431, p. 436 |
| Message-passing machine (new) | Treats the network "essentially as a fast I/O device" (nCUBE/2, iPSC, CM-5). | p. 431 |
| Overlap of communication and computation (new) | The real architectural issue, replacing "latency tolerance". It needs low-overhead asynchronous communication. | p. 431 |
| Split-phase operation (new) | Remote PUT/GET that returns at once, with completion signalled by a flag (Split-C). | p. 434 |
| Lack of locality in message-driven processors (new) | A context lasts only one handler, so large register sets cannot be used, which limits processing performance. | p. 435–437 |
| Threaded Abstract Machine, TAM (new) | A compiler-managed execution model on Active Messages, with inlets as handlers, threads, and two-level scheduling in activation frames. | p. 437 |

- **Verdict after full text (decided at gate 3c, 2026-10-06: include under I2, I1(b) partly):**
  - X3 is partly true of the paper's own implementations. The nCUBE/2 and CM-5 are distributed-memory multicomputers whose kernels fail I1(c), and the Active Message layer sits on their network interfaces (p. 431–433).
  - X3 does not fit the paper as a whole. §3 analyses the J-Machine and Monsoon, where message send and reception are processor mechanisms (SEND instruction, hardware scheduling queue; p. 436, p. 438). §4 proposes processor mechanisms for message handlers: PC injection, user-level interrupts, message registers, a dual message processor (p. 438–439).
  - The paper also meets I2. It evaluates architectures it calls "message driven" and states a reason for their processing performance (lack of locality; p. 435–437, p. 440). I2 exempts the paper from X2. X3 has no I2 exemption in criteria.md, but its condition is not met by the message-driven machines.
