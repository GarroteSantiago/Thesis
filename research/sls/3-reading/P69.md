## First pass: the five Cs
- **Category:** An architecture proposal (design) for one processing node of a message-passing MIMD computer. It is evaluated only with instruction-level and register-transfer-level simulators (abstract; pp. 189, 195).
- **Context:** Message-passing computers built from conventional microprocessors (Cosmic Cube, Intel iPSC, S-NET), with about 300 µs software overhead per message. Single-chip nodes: N-CUBE, Mosaic and the Transputer. Multiple register sets in the Z-80 and the Xerox Alto. Actors [1] and the authors' own network work [5, 6] (pp. 190, 196).
- **Correctness:** The premise is that network latency has fallen to "a few microseconds making software overhead a major concern" (p. 190). The comparison baseline (300 µs, p. 190) is stated with no source or configuration. The proposed node's own times are simulated cycle counts, and the clock period is only expected ("We expect the clock period of our prototype to be 100ns", p. 195).
- **Contributions:** Messages are executed directly by a message unit (MU) that buffers or dispatches them in hardware, with one primitive message, EXECUTE (p. 191). A memory-based instruction set with two priority register sets gives fast context switches (pp. 189, 196). On-chip memory with both indexed and associative access is used for object-ID translation and method lookup (pp. 189, 193). Tags support futures and uniform local/remote access (p. 194).
- **Clarity:** Short and clearly organised: user architecture, micro-architecture, execution model, performance (p. 190). The performance section is a single table of simulated cycle counts (p. 195). The scan's OCR layer is noisy, so Table 1 was checked against the rendered page image.

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| new: message-driven processor | A processing node whose "controller is driven by the incoming message stream". Each arrival schedules a code sequence. | pp. 189, 191 |
| new: direct execution of messages | Overhead is reduced "by directly executing messages rather than interpreting them with sequences of instructions". "no instructions are required to receive or buffer the message". | pp. 189, 191 |
| new: single primitive message (EXECUTE) | Only EXECUTE <priority> <opcode> <arg>… is hard-wired. Richer messages are ROM macrocode, and the paper says they run "almost as efficiently" as hard-wired ones. | p. 191 |
| new: message unit / instruction unit split | The MU receives, buffers and vectors. The IU "simply executes instructions". | pp. 189, 192, 195 |
| new: memory-based architecture for fast context switches | Instructions read or write on-chip memory in one cycle. With four general registers, a context saves or restores in under 10 cycles. | pp. 189, 191, 196 |
| new: priority register sets | Two register sets, one per priority level, so a low-priority message is preempted "without saving state". | pp. 189, 191 |
| new: associative (set-associative) memory | The same on-chip memory is accessed by address or by content. It is used to translate object IDs to node and address, and class+selector to a method address (a method cache). | pp. 189, 193 |
| new: global name space / object identifiers | Global object IDs are translated at run time. Code is kept as one distributed copy. Local and non-local objects are handled uniformly through tags and traps. | pp. 189, 194, 196 |
| new: futures via tags | A reply target is tagged "context future". Use before the reply suspends the context. | pp. 190, 194–195 |
| new: fine-grain concurrency (grain size) | The natural grain is "about 20 instruction times". The MDP aims at about 10 instructions, against several hundred on existing machines. | pp. 190, 195 |
| new: congestion as governor (no send queue) | With no send queue, network congestion blocks producing objects. | p. 191 |

## Notes
- **Source and version:** ACM Digital Library publisher PDF of the ISCA '87 paper (© 1987 ACM, pp. 189–196), not the 1998 reprint (10.1145/285930.285993). dl.acm.org returned HTTP 403 to direct download, so the identical PDF was taken from the Internet Archive snapshot of https://dl.acm.org/doi/pdf/10.1145/30350.30372 (timestamp 20240413161934) and saved as `papers/P69.pdf`. It is a scan with an OCR text layer. Table 1 (p. 195) was checked on the rendered page image.
- **Criterion:** screening's I1 is confirmed: the message-transmit instruction (I1(a), p. 192) and hardware message buffering and dispatch (I1(b), pp. 191–192). No exclusion criterion applies. It is not X3: the message mechanism is in the processor itself, not only in the network interface (pp. 189, 191). It is not X4: the node is for general concurrent programs and is described as an emulator for "other programming models" (p. 196). I2 is not met, because this is a design proposal, not a retrospective or evaluation of an existing architecture.
- **Relation to P12:** this paper is the 1987 architecture proposal of the MDP. From this paper alone, the design read here (single EXECUTE message, two priority levels, 4K-word memory-based node, expected 100 ns clock; pp. 189–191, 195) is a design stage with simulated results only. Whether the results overlap P12's (X8) is for the gate. This record was written from P69 alone.
- The comparison figure of "about 300µs" for Cosmic Cube, iPSC and S-NET (p. 190) carries no citation or measurement setup in the text.
- **Overlap (gate 3c, 2026-10-12):** same machine line as P12 (MDP chip, 1992) and P64 (J-Machine, 1989). Kept: P69 holds the 1987 design and simulated cycle counts (Table 1, p. 195) the others lack.
