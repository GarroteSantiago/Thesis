# P10

## Reference
Colwell, R. P., Gehringer, E. F., Jensen, E. D. (1988). *Performance Effects of Architectural Complexity in the Intel 432*. ACM Transactions on Computer Systems 6(3), 296–339. https://doi.org/10.1145/45059.214411. Included under I1 and I2 (Send instruction, I1(a), p. 298).

## Deepest pass
3

## First pass: the five Cs
- **Category:** Evaluation of an existing object-based processor (Intel 432) by cycle-level simulation, with "what if" modelling of design changes; ends with a retrospective verdict (p. 299–300, 328, 337–338).
- **Context:** The RISC versus CISC / "functional migration" controversy: critics claim a complex architecture is inherently less efficient than a simple one with good software (p. 296). Builds on the Berkeley 432 measurements of Hansen et al. [13] (p. 309), Colwell's CMU thesis [5] (p. 304, 325, 328, 338) and Gehringer and Colwell's procedure-call paper [10] (p. 309, 338).
- **Correctness:** Assumes that only incremental changes, checked with the 432's silicon architects, are fair (p. 300); that cycle savings measured per category from simulator logs can be combined after adjusting for overlap (p. 333); that cross-machine comparisons with different languages (Ada vs C/Pascal) and technologies are hard to draw conclusions from (p. 309) and a "rough estimate" (p. 336). The remaining 2–3x gap is attributed to object orientation as a residual, not measured directly (p. 336).
- **Contributions:** (1) A breakdown of the 432's lost cycles by cause (compiler, alignment, literals, caches, registers, buses) (p. 311–328); (2) a "synthetic 432" showing, in the authors' words, that "from 35-45 percent" of cycles were wasted by errors unrelated to object orientation (p. 330), though the table it refers to gives 2.2–93.7 % by benchmark, with only the CFA rows (39.6–44.7 %) near that range (Table XVI, p. 329); (3) an estimate of the inherent cost of the 432's style of object orientation (p. 336–337); (4) the conclusion that the 432's performance was "dominated, in large part, by artifacts and not by concepts" (p. 338).
- **Clarity:** Clear structure and many tables; some numeric ranges in the text do not match the tables or each other (see Notes). The available scan has OCR errors in table labels.

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| new: functional migration | Moving functions that other systems perform in software (OS functions, high-level-language operations, object addressing and checks, fault handling) into microcode and hardware. | p. 296, 298–299 |
| new: object model | The 432's common semantic model supporting both data abstraction and domain-based operating systems; all information is encapsulated in protected objects. | p. 297 |
| new: protected pointer (capability, Access Descriptor) | A pointer the user program cannot manipulate directly; only microcode creates and manipulates it; carries the rights the bearer has to the object. | p. 302–304, 306 |
| new: two-level addressing | AD to Object Table Directory and Object Table to physical address; separates object location, size and type from the rights programs have to them. | p. 304–305 |
| new: entered environment and object qualification | An object must be "entered" and "qualified" (type, length, rights checked, base/length cached) before use; the 432 provides three entered environments per context. | p. 303–304, 308, 320 |
| new: refinement (Message object) | The procedure-call Message object is a refinement of the calling context, which saves the caller a cache miss but makes the callee traverse the refinement. | p. 307, 323 |
| new: transparent multiprocessing | The object model lets the 432 run on a variable number of processors without recompiling software. | p. 297 |
| new: cycle sink | A cause of lost cycles measured from simulator logs (compiler, alignment, literals, caches, registers, buses). | p. 310, 330 |
| new: synthetic 432 | A hypothetical 432 with the design and compiler errors corrected and incrementally better technology, used to isolate the cost of object orientation. | p. 328–329 |
| new: inherent cost of object orientation | The remaining performance gap (2–3x, or 1–4x) of the improved 432 against conventional processors, attributed to the 432's specific set of object-orientation decisions, not to object-based systems in general. | p. 336–337 |
| new: artifacts vs concepts | The 432's performance was "dominated, in large part, by artifacts and not by concepts". | p. 338 |
| new: compiler-protected intra-module call | Protection of intra-module calls left to the compiler, with only inter-module calls protected by the architecture. | p. 315–316 |

## Notes
- **Source:** full text read from the PDF in the Internet Archive item `432_complexity_paper` (file `10.1.1.140.5969.pdf`, a CiteSeerX scan of the published ACM TOCS version, 44 pages = pp. 296–339, with ACM header and page numbers). The ACM Digital Library PDF (the OpenAlex/Semantic Scholar open-access link) returned HTTP 403, and its Wayback Machine capture could not be loaded. Saved as `research/papers/P10.pdf`. Journal page = PDF page + 295. The scan's OCR garbles some labels (e.g. "1966" for 1988 in footers, "A&r" for Acker); values were read from the page text.
- **Pass:** pass 3, meaning every section and table was read and figures were checked across tables and against the abstract and conclusions (see the inconsistencies below). The arguments were not re-derived from the simulator data, which is not available.
- **Internal inconsistencies found (p.):** text says the CFA benchmarks show a "30–40 percent reduction" (p. 329), but Table XVI shows 39.6–44.7 % (p. 329); Table XXI lists Sieve "cycles saved" and "improved cycles" both as 4,489,605 (p. 336), which cannot both be right; the inherent-cost ratio is given as "one-fourth to one times the speed" (p. 296) and "one to four times slower" (p. 337), which say the same thing (1–4x, across all benchmarks), while the Dhrystone-only figures are 3–4x before the technology allowance and 2–3x after it (p. 336).
- **Criteria:** besides I2, the paper describes an instruction set with a Send instruction named an "interprocess communication primitive" (p. 298), which may also satisfy I1(a); R0-010 records I2 only.
- **Related work to snowball:** Cox et al. 1983, "Interprocess communication and processor dispatching on the Intel 432", ACM TOCS 1(1) (ref [6], p. 338), which by its title should describe the Send/port mechanism this paper does not (the text never cites it); Gehringer and Colwell 1986, ISCA (ref [10], p. 338) holds the procedure-call analysis; Colwell's 1985 CMU thesis CMU-CS-85-159 (ref [5], p. 338) holds the details omitted for space (p. 328).
