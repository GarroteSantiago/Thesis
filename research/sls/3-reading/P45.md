Proceedings of the ACM SIGOPS 22nd Symposium on Operating Systems Principles (SOSP '09), Big Sky, Montana, pp. 221–234. https://doi.org/10.1145/1629575.1629597

## Deepest pass

## First pass: the five Cs
- **Category:** design, implementation and evaluation of an operating system (a multikernel built from microkernels), measured on running hardware (p. 1–2, 9).
- **Context:** builds on Singularity and its channel message passing ("We built Helios by modifying the Singularity [13] operating system", p. 2; Fähndrich et al. [6], p. 3, 5). Places itself after Mach's network-transparent IPC (p. 12), after offload work on channel processors, Auspex, SPINE, AsyMOS and Piglet (p. 12), and next to the multikernels Hive, Cellular Disco and Corey and to Barrelfish ("complimentary efforts at managing heterogeneity", p. 12–13).
- **Correctness:** the main assumptions are stated. Programmable devices are assumed to provide "a timer, an interrupt controller, and the ability to catch an exception (i.e., trap)" (p. 2). The memory and PCI "network" between kernels is assumed "very robust compared to traditional LAN or WAN networks", so "traditional distributed systems protocols (e.g., TCP) are not required" (p. 3). Software isolation through type safety is assumed sufficient to protect processes that all run in ring 0 (p. 4, 6). The assumptions look plausible for the two platforms tested. The evaluation uses one XScale card and one two-domain NUMA machine (p. 9, 13).
- **Contributions:** satellite kernels that "export a single, uniform set of OS abstractions across CPUs of disparate architectures" (p. 1); remote message passing that "extends a standard microkernel message-passing abstraction to a satellite kernel infrastructure" (p. 1); affinity, a placement hint expressed on message-passing channels (p. 1–3); two-phase compilation from CIL (p. 2, 4). Results reported: "up to a 28% performance improvement by offloading tasks to the XScale I/O card" and "a 39% improvement in performance by automatically splitting the application among multiple NUMA domains" (p. 1).
- **Clarity:** clearly written, with explicit design goals (p. 2). Some numbers in the text do not match the figures (see Notes).

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| new: satellite kernel | A microkernel, "composed of a scheduler, a memory manager, a namespace manager, and code to coordinate communication between other kernels", run on each programmable device and each NUMA domain, exporting the same OS abstractions. | p. 1–2 |
| new: coordinator kernel | "The first satellite kernel to boot", which discovers devices, launches the other kernels and manages the namespace. | p. 2, 4, 6 |
| new: remote message passing (RMP) vs local message passing (LMP) | Both implemented "beneath the same inter-process communication abstraction". LMP is zero-copy within a kernel; RMP marshals and copies once between kernels' exchange heaps. | p. 3, 6–7 |
| new: shadow endpoint | Per remote channel, endpoints B0 and A0 shadow the remote endpoint's state, so the original channel interface is preserved. | p. 6 |
| new: affinity (positive, negative, self-reference, platform) | An integer on a message-passing channel in the process manifest. Positive: "prefers local message passing"; negative: "non-interference"; self-reference: copies run on different kernels; platform: preference for a kind of kernel. Hints used only at process start. | p. 3, 7–8 |
| new: centralised namespace | "The namespace is the only component of Helios that relies on centralized control." | p. 6 |
| new: NUMA as a shared-nothing multiprocessor | Each NUMA domain runs its own kernel and manages its own resources; processes may not span domains. | p. 1, 5 |
| new: software isolation (from Singularity) | Processes isolated by type and memory safety, all in one address space at ring 0, so no MMU is required. | p. 4, 6 |
| new: channel contract and exchange heap (from Singularity) | A Sing# contract defines a state machine of legal messages on a channel; message data lives in an exchange heap whose ownership is checked at compile time. | p. 5 |
| new: two-phase compilation | Ship CIL; compile to each available ISA after install. | p. 2, 4 |

## Notes
- **Source:** full text, the authors' camera-ready copy at https://www.sigops.org/s/conferences/sosp/2009/papers/nightingale-sosp09.pdf (PDF from `helios.dvi`, 5 Aug 2009, 14 pages), saved as `papers/P45.pdf`. The Microsoft Research copies returned HTTP 403. There are no printed page numbers, so pages are PDF pages; publisher pages 221–234 (Crossref), offset +220. All 14 pages read, figures inspected as images (third pass).
- **Criterion:** the full text confirms I1(c). "all other operating system services, including device drivers, execute as processes and use message passing for communication" (p. 3), and the kernels coordinate through remote message passing (p. 2). This is a kernel, not a library on a conventional kernel, so X2 does not apply. It runs on one machine, so X3 does not apply. No criterion change.
- **Text and figure mismatches** (reported, not resolved):
  - p. 9 says "once messages are greater than 32 KB in size, message passing over the PCI-E bus is more efficient than message passing between two NUMA domains". In Fig. 5 (p. 10) the RMP NUMA curve passes above RMP XScale between 4 KB and 8 KB (read off).
  - Fig. 11 (p. 12) goes from 20.7 s to 17.7 s, about 14.5% less time (computed). The text says "improved by only 10%".
  - Fig. 10 bars read off as about 60 and about 79 emails/s (about +32%). The text says 39%. The bar reading is imprecise.
- **Percentages:** "68% faster" (p. 11) and "28% faster" (p. 11) match a reduction in run time (about 24 to 7.6 s; about 248 to 178 s, read off), not a throughput ratio.
- **For SQ1 and SQ2:** the paper keeps system calls on purpose because "Local message-passing is slower than a system call" (p. 2). Remote messages between kernels are built on shared memory and DMA (p. 7). Message passing is exclusive between processes, not inside the kernel or inside a process.
- **Other related systems** cited, not yet in the review: Singularity [13], Fähndrich et al. EuroSys '06 [6], Hive [4], Barrelfish [28], Mach [1], Corey [2], K42 [30], Tornado [10] (p. 12–13). Possible snowballing leads.
