# P102

## Reference
David Wentzlaff, Anant Agarwal (2009). *Factored Operating Systems (fos): The Case for a Scalable Operating System for Multicores*. ACM SIGOPS Operating Systems Review 43(2), pp. 76–85. https://doi.org/10.1145/1531793.1531805

## Deepest pass
2

## First pass: the five Cs
- **Category:** A position and design paper with motivating measurements. It argues that SMP operating systems cannot scale to "1000+ core systems" (p. 2), measures two Linux scaling problems (p. 3–4), and describes the design of a new message-passing OS (fos) whose prototype is "under active development" (p. 2, p. 8). fos itself is not evaluated.
- **Context:** Microkernels (Mach, L3, L4; p. 2, p. 8), scalable shared-memory kernels (Tornado/K42, Hive, Disco/Cellular Disco, Corey; p. 9), distributed OSes (Amoeba, Sprite, Clouds; p. 9) and distributed Internet services (DNS, BitTorrent, Chord, AFS, GFS; p. 9–10). The authors' own Raw and Tilera on-chip networks are cited for message costs (p. 8).
- **Correctness:** The Linux measurements are on real hardware (p. 3), and the cache study runs in a QEMU-based simulator (p. 4). The case for fos rests on argument, for example "We believe that the shared nothing, message passing only, approach will encourage OS developers to think very carefully about exactly what data is being shared, which will lead to more scalability" (p. 5). The paper names its own open questions in Section 3.4 (p. 8).
- **Contributions:** (1) A measurement showing that the Linux 2.6.24.7 physical page allocator "does not scale beyond 8 cores under heavy load" (p. 2, Fig. 1 p. 3). (2) A simulated measurement of OS/application cache interference on Apache2 (p. 4). (3) Three recommendations: avoid hardware locks, separate OS from application cores, and avoid global cache-coherent shared memory (p. 5). (4) The fos design: a microkernel with mailbox messaging, OS services split into fleets of servers bound to cores, a name server, and space multiplexing instead of time multiplexing (p. 5–7).
- **Clarity:** Well structured and readable. The figure labels in the author PDF use an odd font encoding (the text cannot be extracted), but the rendered figures are legible. The message format is not described.

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| factored operating system (fos) (new) | An OS "factored into function specific services", each "distributed into spatially distributed servers" that "collaborate and communicate only via message passing" | p. 5 |
| space multiplexing replaces time multiplexing (new) | "Scheduling becomes a layout problem not a time multiplexing problem"; the OS "runs on distinct cores from applications" | p. 5 |
| fleet (new) | The set of servers of one type that together provide one OS function, e.g. physical memory allocation, file system, scheduling | p. 6 |
| fos client (new) | "The code executing on a single core under the fos-microkernel"; applications and OS servers "act as peers" | p. 6 |
| receive mailbox (new) | A named, protected endpoint owned by a client, with a large buffer in the receiver's address space; a send to a full mailbox returns an error | p. 6, 8 |
| message proxy library / translation library (new) | Turns a traditional system call into a message to an OS-layer server and unpacks the reply | p. 6 |
| microkernel to OS layer delegation (new) | The microkernel delegates naming and privilege to OS-layer fleets, caches their answers, and avoids cycles by knowing the delegates' locations and granting static privileges ("privilege fixed point") | p. 7 |
| stateless, transaction-oriented server with continuations (new) | A server processes each transaction to completion without preemption, stores a continuation for long-latency operations, and needs no local locking | p. 7 |
| notional lock / lock server (new) | A lock held by a server and acquired by message; "the cost of software-based lock management may dwarf the performance wins of removing traditional locks" | p. 8 |
| OS-application and OS-OS locality aliasing (new) | OS and application working sets competing for implicitly shared caches and TLBs on one core, including "anti-locality cache collisions" | p. 4 |
| best-effort OS interfaces (new) | Interfaces that return information "which may be slightly out of date" for higher performance, with an accurate but slower alternative | p. 2 |

## Notes
- **Source and version:** author preprint PDF, downloaded on 2026-10-07 from https://www.princeton.edu/~wentzlaf/documents/Wentzlaff.2009.OSR.fos.pdf and saved as `papers/P102.pdf` (11 pages, created 2009-03-02, marked "To appear in ACM SIGOPS Operating System Review ... April 2009", p. 1). The ACM PDF returned 403, and Unpaywall lists no open-access copy. The publisher page range 76–85 is from Crossref. Read in full, figures included (second pass).
- **Criterion:** the full text meets I1(c) as screened. The OS layer's servers "communicate only via the messaging interface provided by the microkernel layer" (p. 6), the paper uses the terms "message passing", "send" and "mailbox" (p. 5–6), and fos runs without an underlying conventional kernel (p. 5). No exclusion applies. X2 does not: messaging is the kernel's own mechanism, not a library on a conventional kernel. X3 does not: the target is a single multicore chip (p. 9). X5 does not: a 10-page journal article. The paper may also answer SQ13/SQ14 under I4 (inferred), through its Linux scaling measurements and its named limits of cache-coherent shared memory (p. 3, p. 5). That would not change the include verdict.
- **For SQ10 (model equivalence, I4 field):** fos messages may be carried on shared memory: "The fos-microkernels transport the message to the destination via on-chip networks or shared memory" (p. 6). The cost of doing so is not reported.
- **For SQ11 (model mixing):** "Within an application, communication can be achieved via shared memory communication or messaging", and fos keeps shared memory for applications "if the underlying hardware supports it" (p. 6).
- **For SQ7/SQ8 (defects, what shapes programs):** the paper argues, without counts, that "Adding locks into an operating system is time consuming and error prone" and that locks "can introduce circular dependencies and hence cause deadlocks" (p. 3). It also argues that "global shared memory easily allows the introduction of data races which can be difficult to detect at test time" (p. 5). It expects that "the shared nothing, message passing only, approach will encourage OS developers to think very carefully about exactly what data is being shared" (p. 5). It says "the message passing nature of fos discourages this usage model [lock managers] by making programming in this manner difficult" (p. 7). All of these are argument, not measurement.
- **Open questions the authors name:** whether shared OS structures (virtual memory, buffer cache) "can be accessed with good performance" (p. 8); whether all multi-sequence operations can be written without local locks: "it is not certain that all cases can be handled" (p. 8); whether "a hardware solution or the software solution explored by fos proves more scalable" (p. 8).
