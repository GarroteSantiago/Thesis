## First pass: the five Cs
- **Category:** Implementation paper on a compiler for a language-specialised processor, with a measurement section and estimates of what each hardware feature is worth (pp. 1–10).
- **Context:** Part of the Smalltalk On A RISC (SOAR) project at Berkeley; builds on the SOAR architecture paper [2], the SOAR runtime paper [3], Ungar's dissertation [4] and Bush's report [8]; compares with Deutsch and Schiffman's dynamic translator [5] and with the Xerox Dorado (pp. 1–2, 9).
- **Correctness:** The compiler's own measurements (compile time, code expansion, register use) are reported with workload and machine (pp. 8–10). Most figures about SOAR hardware are taken from other reports: "All results quoted in this paper are found in either Ungar's dissertation [4] or Bush's report [8], unless stated otherwise" (p. 3, footnote 2), and several are called estimates (pp. 1, 6, 8).
- **Contributions:** Describes the bytecode-to-SOAR translator (simulated stack, register allocation in overlapping windows, spill rules) (pp. 2–6); shows how SOAR's tags, traps and pointer-to-register simplify it (pp. 6–7); reports compile time, code expansion and register-window use over the whole Smalltalk-80 image (pp. 8–10); concludes that "Several features supported by the SOAR hardware could easily be performed by the compiler at marginal increased time and space costs" (p. 10).
- **Clarity:** Short and clearly written; the scan is legible though the OCR text layer has errors (numbers were checked against the page images).

## Concepts
| Concept | What the paper says | Page |
|---|---|---|
| new: Smalltalk On A RISC (SOAR) | "a Berkeley RISC processor extended to support Smalltalk", "designed in conjunction with the runtime system" | 1 |
| new: compiling all methods (no bytecodes at run time) | "the canonical representation of a method in the SOAR system is as SOAR instructions, not bytecodes" | 2 |
| new: bytecodes as the semantic definition | "the virtual machine is the semantic definition of the language", so "a correct bytecode compiler is, along with correct system functions, a correct Smalltalk implementation" | 2 |
| new: overlapping register windows | Each window is an activation frame; SOAR uses a 16-register "fully overlapped" window split into high and low sets of 8, with no registers "dedicated solely for local use" | 3–4, 10 |
| new: spilling rules (assignment by category, permanent assignment) | Whole categories of variables spill together, and a variable "cannot be moved once it has been allocated a location"; "reasonable and simple" but not minimal | 4 |
| new: integer tags and traps | Arithmetic is compiled as integer code; on non-integers "the hardware will trap and transfer to a handler that will look up the correct method" | 6 |
| new: generation tags (hardware write barrier for generation scavenging) | Tags on pointers detect "when pointers to new objects are stored into old ones"; the check is in hardware, a trap handler records it | 7 |
| new: pointer to register | Hardware "that maps registers to memory addresses", for references to activation records held in register windows | 7 |
| new: in-line method cache | "we cache the last method called" and check the type of the leftmost operand; justified by "96% of the time the method invoked does not change" | 8 |
